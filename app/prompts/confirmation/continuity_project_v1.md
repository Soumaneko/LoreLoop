# 输出要求

只输出符合 Schema 的 JSON。

ContinuityItem 只允许两类：

- `commitment`：明确的承诺、债务、协议、职责或义务。
- `open_thread`：未完成目标、仍存在的威胁、尚未解开的谜团或待处理事件。

生命周期操作：

- `create`：本轮正文明确建立了一个新的合格事项，并且该事项范围有限、存在可从后续正文判断的完成或解除条件。`premise` 应紧凑记录事项最初成立的原因与原始含义，以及范围边界。
- `update`：活跃事项取得实质进展，或参与者、地点、期限发生明确变化。`state_delta` 只描述本轮发生了什么变化；`new_current_state` 是应用本轮变化后的完整当前快照。
- `resolve`：正文明确完成了承诺或目标、解开了谜团，或者消除了威胁。
- `cancel`：正文明确解除、放弃、否定事项，或使其不再适用。

# 核心规则

1. 每个操作必须引用“本轮已确认正文”中直接支持它的一个或多个 `evidence_id`。
2. 不得引用旧场景、Player Input 或自行编造的证据 ID。
3. 模糊意愿、普通动作、临时状态、关系描述、持有物、能力和一般事实不得创建 Item。
4. 没有明确终点的长期愿景、抽象发展方向或无限延续的常规职责不得创建 Item。Item 必须只追踪一个范围有限、能够明确判断完成、解除或失败的具体事项。
5. 不得为了满足粒度要求，自行把不合格的宏大目标拆分成正文没有明确建立的阶段任务。只有当本轮正文明确建立了具体阶段事项，并且该事项独立满足原有 `create` 门槛时，才可创建；否则 do nothing。
6. 已有活跃 Item 应当 `update` 时，不得重复 `create`。
7. 仅仅提及事项不等于取得进展。本轮没有改变的 Item 不输出任何操作。
   如果本回合与所有 Continuity 无关，或没有产生实质变化，必须直接输出 `{{"operations": []}}`。do nothing 是正常且优先的结果。
8. 同一个 Item 在本轮最多接受一个操作。
9. `state_delta` 只写本轮新确认的变化，不得抄写旧状态。
10. `subject` 是便于识别的短标题；`premise` 和 `state_delta` 都应紧凑，不得复制大段正文。
11. 只在输入支持时使用标准名称；不得臆造参与者、期限、地点、动机或后果。
12. Ledger 中的 `current_state` 是事项此刻的单个紧凑快照。`new_current_state` 必须完整保留仍有效的旧事实，移除或改写已失效、被推翻的判断，并纳入本轮新变化；它只描述“现在是什么状态”，不得记录演化流水账。
13. `update.entities` 只输出本轮新确认、需要加入索引的实体，不必重复旧实体；系统会与旧列表合并，旧实体永不删除。`location`、`deadline` 为 `null` 表示本轮没有更新，必须保留 Ledger 中的旧值；非空值才表示替换。
